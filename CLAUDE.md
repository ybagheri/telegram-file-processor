# CLAUDE.md

Guidance for Claude (or any AI coding agent) working in this repository. Read this before making changes — several of the rules below exist because of real bugs found and fixed during development, not just style preference.

## Project overview

A two-process Telegram bot: `bot.py` talks to the user (aiogram, Bot API), `worker.py` does the actual file processing (Telethon, a real user account — needed to get around the Bot API's small download-size limits). They **never call each other's code directly**; they only exchange small JSON messages through a private Telegram group (the "bridge"), defined in `core/protocol.py`.

Read `docs/architecture.md` for the full picture before making non-trivial changes. It documents the job lifecycle, the bridge protocol, and the archive folder-walk logic in more depth than inline comments do.

## Hard rules

- **`keyboards/files.py`'s `options_keyboard(pid, pending_files)` takes the `pending_files` dict as an explicit parameter, not a module global.** Changed on purpose during the phase-B module split (see the change log below) — don't revert it to reading a global `pending_files` from inside `keyboards/files.py`, and any new call site must pass `bot.py`'s real `pending_files` dict, not a copy.
- **aiogram checks a router's OWN directly-decorated handlers before descending into any included sub-router — regardless of when `dp.include_router(...)` was called.** This bit us for real during the phase-D module split: `handle_private_message`'s bare `F.chat.type == "private"` filter (no further discrimination) was originally decorated directly on `dp`, and after moving `/admin` + admin callbacks onto their own `admin_router`, the catch-all started swallowing `/admin` before the sub-router ever got a chance — verified empirically with `Dispatcher.feed_update(...)` (direct function-call tests never caught it, since they bypass aiogram's routing entirely). **Fix, and the rule going forward: any handler with a broad/catch-all filter must live on its own `Router`, included via `dp.include_router(...)` *after* every more-specific router** (see `catchall_router` in `bot.py`, which wraps `handle_private_message` and is included last, right after `admin_router`). If you add another Router with a specific `Command`/`F.data` filter, include it before `catchall_router`; if you ever need another broad/unfiltered handler, it also needs its own router positioned after the specific ones — never decorate a catch-all directly on `dp` while any sub-router exists, or the sub-router's specific handlers can be silently starved. `tests/test_router_wiring.py` drives real `Update` objects through `dp.feed_update(...)` specifically to guard against this regressing again — keep it passing, and extend it (rather than deleting it) if more routers are added in later phases of the split.
- **`track_pending_user_if_needed(message)` (in `utils/access_control.py`) must be called from every place that checks `is_authorized(...)` for an incoming private message, not just `/start`.** A user's first interaction is just as likely to be sending a file directly (or `/settings`) as it is to be `/start` — see the "fix" change-log entry above for the exact bug this was (an unregistered user sending a file straight away, as `qa-userbot` does, went completely unnoticed). If you add another entry point that gates on `is_authorized(...)`, call this first.
- **Access control is opt-in.** `is_authorized()` in `bot.py` treats an empty `Telegram.ADMIN_IDS` as "no access control configured" — everyone is allowed. Don't change this default; a server with no admin set and access control forced on would lock out the operator with no way to add anyone.
- **`services/access_store.py` is SQLite-backed (`config_data/access.db`), not a hand-written JSON file.** A user's record has `expires_at` (Unix timestamp, `None` = unlimited) and `active` (bool) in addition to identity fields — access is granted only when the user exists, `active` is true, *and* they're not expired (`AccessStore.is_authorized`). On first run against an old JSON-file deployment, `AccessStore.__init__` auto-migrates `authorized_users.json` into the DB once (only if the table is empty) and renames the old file to `authorized_users.json.migrated` as a backup — don't delete that migration step, and don't add a second, competing migration path.
- **`services/settings_store.py` (per-user `/settings` preferences — quality, watermark, upload mode, delivery target, etc.) is also SQLite-backed (`config_data/settings.db`)**, for the same reason and with the same one-time legacy-JSON-migration pattern (`user_settings.json` → `user_settings.json.migrated`). `get(user_id)` stays synchronous and always returns every key from `DEFAULTS` merged with whatever's stored; `update(user_id, **changes)` stays async and validates keys against `DEFAULTS` before writing (raises `ValueError` on an unknown key rather than silently adding a column-less field). If you ever add a new per-user setting, add it to `DEFAULTS` *and* the `CREATE TABLE` column list in the same change — the two are not derived from each other.
- **`services/pending_user_store.py` (`config_data/pending_users.db`) tracks people who `/start`-ed the bot without being in `access_store` yet** — separate table, separate purpose (a lightweight "who showed interest" log for admin notification/reporting, not an access-control decision). `bot.py`'s `start()` handler only touches this table when the user is neither an admin nor already present in `access_store` at all (`access_store.get(user_id) is None` — deliberately *existence*, not `is_authorized`, so a disabled/expired-but-once-registered user is never re-added here). `record_start()` returns whether this is a brand-new pending user (→ notify every admin once via `notify_admins_of_new_pending_user`, then `mark_notified`) or a repeat `/start` (→ only `last_seen_at`/`start_count` bump, no repeat notification, identity fields from the *first* start are preserved). **Whenever an admin actually registers someone into `access_store` (`access_store.add(...)`), the corresponding call must be followed by `pending_user_store.remove(target_id)`** — both current call sites in the `admin_add_user`/`admin_add_username` states do this; if you add a third way to register a user, do the same or they'll incorrectly keep showing up as "pending" after they're already a real user.
- **All SQL values are parameterized (`?` placeholders), never f-string-interpolated — this includes every user-supplied string** (name, username, artist, caption, exclude-text, etc.) that ends up in `access_store`/`settings_store`. The *only* places either store builds SQL text dynamically are (a) `settings_store.update()`'s `SET col1 = ?, col2 = ?` clause, and (b) the legacy-JSON migration's column list — both build the list of **column names** (not values) exclusively from `DEFAULTS.keys()` / a fixed whitelist checked before use, never from arbitrary caller-supplied strings. If you add a new dynamic-SQL code path, keep this shape: values always go through `?`, and any column/table name that varies must come from a hardcoded whitelist, never a raw string. Verified against classic injection payloads (`'; DROP TABLE ...`, `' OR '1'='1`, etc.) stored as inert text with no query-structure change — see the change log entry below.
- **Never delete a user's row just to disable them.** Use `access_store.set_active(user_id, False)` — it preserves `expires_at`/history so re-enabling (`set_active(..., True)`) or renewing (`update_expiry`) later doesn't need the admin to re-enter everything. `access_store.remove()` is for genuinely deleting a record and is a separate, more destructive action.
- **Disabling or deleting a user always goes through `confirm_keyboard(...)` first** — the target is identified, then a yes/no prompt is shown, and the actual `set_active`/`remove` call only happens from the `admin:toggle_confirm:*`/`admin:delete_confirm:*` callback, never from the free-text handler that identified the target. If you add another destructive admin action, follow the same two-step shape rather than acting immediately on identification.
- **`bot.py`'s admin "add/renew/disable a user" flows are multi-step and share two bits of transient state**: `awaiting_state[admin_id]` (which step we're on) and `admin_flow[admin_id]` (scratch data collected so far — chosen duration, target id, typed name). Both live in `state.py` now (phase C of the module split), keyed by the *admin's* user_id, not the target's, and both must be cleared together (see `/cancel` and the terminal branch of each flow) or a later flow will silently pick up stale data from an abandoned one.
- **Never reassign any of the shared dicts in `state.py`** (`pending_files = {}` instead of mutating the existing one, etc.) from any module that imports them. A reassignment rebinds *that module's* local name to a brand-new dict — every other module still holding the original import would silently stop seeing that module's changes. Always mutate in place (`d[key] = value`, `d.pop(key, None)`, `del d[key]`).
- **Never assume a caption is safe to leak.** Every message posted to the bridge group carries a JSON payload as its caption/text (`Protocol.encode(...)`) so the other process can read it. When relaying anything from the bridge to an end user (`handlers/bridge.py`'s `handle_bridge_message`), **always pass an explicit `caption=` override** — `aiogram`'s `copy_message` keeps the *original* caption when `caption=None`/omitted, which means the internal JSON leaks straight to the user if you forget this.
- **`Job` uses `slots=True`.** You cannot assign a new attribute that isn't declared as a dataclass field — it raises `AttributeError` at runtime, not at import time, so it's easy to miss until it actually executes. If you need a new piece of job-level state, add it as a real field in `core/job.py`.
- **A single archive `Job` produces many `OutputFile`s of different kinds.** Don't put per-output metadata (kind/title/artist/thumbnail/duration) on the shared `Job` — it gets overwritten as the archive processor walks from file to file, which was a real, hard-to-spot bug. Always attach it to the `OutputFile` entry returned by `job.add_output(...)`.
- **`job.options.rename_to` is neutralized during archive extraction** (`ArchiveProcessor` saves/restores it around the walk). If you touch that logic, keep the neutralization — otherwise every file in an archive collapses onto the same renamed output name.
- **Compare `MessageType` values, not raw strings**, when branching on `payload["type"]` — a previous version compared against `"JOB"` (wrong case) while the enum value was `"job"`, and the whole pipeline silently never processed a single job.
- **New processors register themselves** via `@register_processor("TYPE")` from `core/registry.py` (see `processors/*.py`). Don't add a new if/elif branch to `dispatcher/dispatcher.py`.
- **`.rar` handling shells out to the real `unrar` CLI, not the `rarfile` Python package.** `rarfile` is just a thin wrapper around `unrar`/`unar`/`bsdtar` and turned out to have real gaps around partial multi-volume sets; `processors/archive.py` now calls `unrar` directly (`v` to list, `x` to extract one member) and parses its text output. If you change this, keep testing against `unrar`'s actual output format (there's a regression risk here since output format can vary slightly by version — the parsing regex was built and tested against real `unrar 6.11` output). The real (non-free) `unrar` build must be installed and on `PATH` — Debian's default `unrar-free` package has known RAR5/multi-volume gaps and is not sufficient (see `Dockerfile`).
- **Multi-volume RAR archives are handled by `ArchiveProcessor.process_multivolume`**, a separate path from the normal single-file `process()`. It downloads volumes on demand (never all of them upfront) using a safety window sized from each entry's *real* compressed size vs. the volume size — never guessed — specifically so a volume is never deleted while some pending file might still need it. If you touch this, preserve that safety property; a wrong guess here means silent, unrecoverable data loss for the user, not just a retryable error.
- **`config.py` validates env vars at import time.** Any module that imports `config` (directly or transitively) will raise `RuntimeError` without `API_ID`/`API_HASH`/`BOT_TOKEN`/`GROUP_ID`/`SESSION_NAME` set in `.env`.
- **Telegram's thumbnail limit is 320×320.** `services/media.py`'s `generate_thumbnail`/`normalize_thumbnail` already scale down to fit; don't bypass them with a raw ffmpeg call that skips the `scale=` filter, or the thumbnail will be silently ignored by Telegram.
- **Watermark logo is resized per-video**, to fit within 1/5 width × 1/5 height of the *output* video (not the logo's native size) — see `LOGO_POSITIONS` and the `scale=` step in `services/media.py:convert_video`. This is intentional, not a leftover bug.
- **Always wrap Telegram sends in a retry for `telethon.errors.FloodWaitError`** when the call could plausibly run in a loop (per-file uploads, per-folder announcements). See the retry-once pattern in `worker.py` and `processors/archive.py` — copy it rather than reinventing it.
- **Never let one bad output file abort a whole batch.** The upload loop in `worker.py` deliberately catches per-file exceptions and keeps going — an archive can produce hundreds of files, and one corrupt one shouldn't cost the other 299.

## Conventions

- Async everywhere in `processors/`, `services/telegram.py`, `worker.py`, `bot.py`. Blocking calls (`zipfile`, `py7zr`) go through `loop.run_in_executor(...)`; `.rar` handling shells out to the real `unrar` CLI via `asyncio.create_subprocess_exec` (see the note below — not the `rarfile` Python package).
- User-facing strings (bot replies, button labels) are in Persian, matching the actual audience. Code, comments, docs, and identifiers are in English.

## Change log

Dated entries for anything user-facing or architecturally significant, newest first. Keep this updated when you make a non-trivial change — it's how the next session (human or AI) knows what already happened without re-reading every diff.

- **2026-08-28 — `MAX_FILE_SIZE` is now actually enforced (it was defined but never checked).**
  `worker.py`'s `process_job` checks `message.file.size` (Telegram's declared size, known before any bytes move) against `Processing.MAX_FILE_SIZE` right after the file metadata is read and *before* `telegram_service.download(...)` — on overrun it sends a `Protocol.create_error(...)` through the bridge (Persian message via the new `_file_too_large_message` helper, relayed by `handlers/bridge.py` with the usual "❌ خطا:" prefix) and aborts cleanly with `job.cleanup()`. `process_multipart_job` applies the same rule to the *sum* of all declared part sizes, so a multi-volume set isn't a way around the limit. `MAX_FILE_SIZE` (default 5 GiB, env-configurable) is now documented in README's environment-variable table and the Usage section. New `tests/test_worker_guards.py` (4 tests): oversized single file rejected before `download` is ever called (the stub raises if touched), a file exactly at the limit still proceeds to download, an oversized multi-volume total rejected before any volume is fetched, and the message-formatting helper.

- **2026-08-28 — Free-disk-space guard before downloading/extracting large files.**
  New pre-download check in `worker.py` (both `process_job` and `process_multipart_job`, applied right after the `MAX_FILE_SIZE` guard): when the declared size is above `Processing.DISK_SPACE_CHECK_THRESHOLD` (env, default 256 MiB — smaller files skip the check, it'd be noise), `_has_enough_disk_space` requires `shutil.disk_usage(path).free >= declared_size * Processing.DISK_SPACE_SAFETY_FACTOR` (env, default 2.0) on **each** of `Paths.DOWNLOADS`, `Paths.TEMP`, `Paths.OUTPUTS` (checked individually so a bind-mounted path is still covered); on shortfall the job is rejected via `Protocol.create_error(...)` ("فضای دیسک سرور برای پردازش این فایل کافی نیست…") and `job.cleanup()`. The factor deliberately covers input + working space (ffmpeg output, extraction) only — it does not try to reserve room for a fully-expanded archive, which would defeat `ArchiveProcessor`'s streaming approach (that processor was not touched). 4 new tests in `tests/test_worker_guards.py` (headroom math below/above threshold + safety factor, low-space rejection before download with the Persian message, small files skipping the check even with ~zero reported free space); the existing guard-test fixture now stubs `shutil.disk_usage` with plentiful space by default so the older tests still isolate the size guard. Env vars documented in README; guard explained in `docs/architecture.md`'s job-lifecycle section.

- **2026-08-28 — Per-job concurrency limit (`MAX_CONCURRENT_JOBS`, default 2).**
  `worker.py` now wraps the actual processing step (not the download) of both `process_job` and `process_multipart_job` in a shared `asyncio.Semaphore` (`_get_processing_semaphore()`, lazily created from `Processing.MAX_CONCURRENT_JOBS`, env-configurable, clamped to ≥ 1) — so at most N jobs run ffmpeg/extraction at once on the VPS and the rest queue instead of launching unbounded parallel processing. Ordering: bridge events spawn job tasks in arrival order and `asyncio.Semaphore` wakes waiters FIFO, so queued jobs still *start* processing in the order they arrived (downloads overlap freely, only the heavy step is bounded). An exception inside the `async with` releases the slot, so a crashing job can't starve the others. The semaphore is shared between single-file and multi-volume jobs — a multi-volume extraction counts as one slot. New `tests/test_worker_concurrency.py` (5 tests): concurrency stays at the configured cap with 5 parallel jobs, a failing job releases its slot for the next ones, jobs begin processing in arrival order under a limit of 1, and the semaphore value is built from the config (including the ≥1 clamp). Env var documented in README; noted in `docs/architecture.md`'s job-lifecycle section.

- **2026-08-28 — Basic per-user file-submission rate limiting in the bot.**
  New pure helper `utils/rate_limit.py` (`prune_timestamps`/`is_rate_limited`/`record_submission` — sliding window over submission timestamps, `max_files <= 0` disables it) + a shared `user_submission_times: dict[int, list[float]]` in `state.py` (mutated in place, pruned per check). `handlers/core.py`'s `handle_private_message` calls `check_submission_rate_limit(user_id, message)` right after a new file (document/video/audio) is detected and **after** `is_authorized(...)` — it sits alongside the access check, never replaces it, and never blocks password replies or `file:*` awaited-input flows (only fresh submissions are counted). Over-the-cap users get `_rate_limit_text(...)` ("⛔ شما در N دقیقه گذشته بیش از حد مجاز (M فایل) ارسال کرده‌اید…"). Config: `RATE_LIMIT_MAX_FILES` (default 5) and `RATE_LIMIT_WINDOW_MINUTES` (default 10), both env-backed; the dict entry is dropped once a user's history prunes to empty so it can't grow unboundedly. Plain photos (watermark flow) are deliberately not counted — they can't enqueue heavy processing. 10 new tests in `tests/test_rate_limit.py` (window pruning in place, cap boundary, expiry, disable-at-zero, per-user isolation, allow-then-reject sequence through the real handler helper). Env vars documented in README's table and Usage section.

- **2026-08-28 — Bridge heartbeat + admin `/status` (worker liveness).**
  New `MessageType.HEARTBEAT` (`core/constants.py`, additive — no existing type changed) and `Protocol.create_heartbeat()` (`core/protocol.py`), which deliberately carries **no** `user_id` so it can never be treated as something to relay to a user. `worker.py` runs `heartbeat_loop()` (task started from `main()`), sending one heartbeat through the bridge every `Heartbeat.INTERVAL_SECONDS` (`HEARTBEAT_INTERVAL_SECONDS` env, default 300); send failures are logged and retried next tick — a missed heartbeat never takes the worker down. `handlers/bridge.py` recognizes the type *before* the existing `if not user_id: return` gate and only stamps `state.py`'s new `worker_last_seen: dict[str, float]` (key `"worker"`, mutated in place) — nothing is ever delivered to a chat. New admin-only `/status` command in `handlers/admin.py` (same `is_admin` gate as `/admin`) reports "worker seen recently ✅ / stale ⚠️ / never seen ❌" via the pure `format_worker_status(last_seen, now, interval)` helper (grace window = interval + 60 s, staleness shown in whole minutes). 7 new tests in `tests/test_heartbeat.py` (factory round-trip + no-`user_id` assertion, bridge tracking updates the dict and relays nothing, non-heartbeat payloads without `user_id` still don't mark it seen, and the three staleness branches incl. the threshold boundary). Env var + `/status` documented in README; `heartbeat` row added to `docs/architecture.md`'s bridge-protocol table.

- **2026-08-28 — URL-upload feature: send a direct download link instead of a file.**
  New usage mode. **Bot side** (`handlers/core.py`): a private, authorized user's message that is *just* an http(s) link (`utils/url_validation.py::extract_url` — deliberately strict, surrounding prose disqualifies it) goes to `handle_url_submission`: `validate_url` enforces http/https-only plus an SSRF guard (host IP literals *and* every DNS-resolved address checked against loopback/private/link-local/reserved/multicast ranges — 127.0.0.1, 10.x, 192.168.x, 172.16.x, 169.254.x metadata, ::1, ... all rejected), then the shared per-user rate limit, then type detection from the URL's filename (`filename_from_url` — query stripped, percent-decoded); unsupported/unknown types are rejected in Persian *before* anything downloads. - **2026-07-28 (phase 3) — Near-expiry reminder DM, plus a SQL-injection audit of the SQLite migration.**
  New background task `expiry_reminder_loop()` in `bot.py` (started from `main()` alongside polling) checks every `REMINDER_CHECK_INTERVAL_SECONDS` (6h) for active users whose access expires within `REMINDER_THRESHOLD_SECONDS` (3 days) and DMs each one once. `access_store` gained a `last_reminder_expiry` column (added via a `PRAGMA table_info` + `ALTER TABLE` check in `_migrate_schema()`, so existing deployments upgrade in place) plus `list_expiring_soon()`/`mark_reminded()`; renewing a user's expiry (`update_expiry`) or re-adding them (`add`) resets that marker so they get a fresh reminder cycle for the *new* date rather than staying silently suppressed. A user who's blocked the bot still gets marked reminded (logged, not retried every cycle) instead of erroring the whole pass. The single-pass logic is split into `check_and_send_expiry_reminders()` specifically so it's testable without waiting on the sleep loop.
  Also: audited both stores for SQL injection risk (prompted by a direct question — every value a user can influence, e.g. name/username/artist/caption/exclude-text, goes through `?` placeholders; verified empirically with classic payloads like `'; DROP TABLE ...` and `' OR '1'='1` stored as inert text, table untouched). The only dynamic-SQL construction (`settings_store.update()`'s SET clause, and the legacy-JSON migration's column list) builds column *names* only from a fixed whitelist (`DEFAULTS.keys()`), never from caller-supplied strings — see the hard rule above.
